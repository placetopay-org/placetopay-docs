# Procesamiento con cuentas bancarias

 Para procesar transacciones utilizando como instrumento de pago una cuenta bancaria se requiere implementar el instrumento de pago account que permite definir los datos de la cuenta a utilizar, así como los mecanismos para hacer validación de la cuenta utilizando servicios de validación de cuentas como: Account Validator.

Tipo | Descripción
---------|----------
 SAV | Cuenta personal de ahorro 
 DDA | Cuenta cheque personal 
 CCD | Cuenta comercial


##  Validación de cuentas 

Para garantizar la seguridad en el procesamiento de cuentas bancarias se recomienda utilizar el servicio de validación de cuentas bancarias Account Validator.

Con este servicio antes de iniciar el pago se requiere que el dueño de la cuenta realice una operación de verificación en una interfaz gráfica.

Una vez que el dueño de la cuenta completa este proceso se consulta el servicio via API y se obtiene el objeto Account con un código de verificación entregado por el servicio.

La API de procesamiento se encargará de validar este código entregado por Account Validator y determinar si la cuenta a pasado las validaciones, de no ser así no se continuará con el procesamiento.

## Tokenización

Una cuenta bancaria puede ser tokenizada de tal manera que se pueden hacer cobros a dicha cuenta sin que el dueño de la cuenta esté presente.

En este flujo una vez la cuenta se ha validado se puede generar un token que representa a la cuenta y puede usarse para realizar nuevas transacciones.

Revisa la sección de  [Tokenization](/gateway/api/reference/tokenize) de la API.

## Simulador de devoluciones ACH (ACH Return)

<Note>
    Este simulador es exclusivo del ambiente de pruebas (`test`). **No** reproduce el proceso real de generación de devoluciones ACH entre Placetopay y las redes bancarias, y **no implica ningún tipo de certificación**, ni de tu integración ni entre Placetopay y los procesos de retorno. Su único objetivo es que puedas validar en pruebas los eventos, estados y notificaciones (Webhooks) que recibirías si se presentara una devolución ACH real en producción.
</Note>

En producción, las devoluciones ACH (ACH Returns) son generadas por procesos externos a Placetopay y posteriormente capturadas, enriquecidas y notificadas vía Webhook. Ese flujo no puede replicarse de forma real en pruebas, por lo que se habilitaron cuentas de prueba con un comportamiento fijo, asociado al número de cuenta. Funciona igual que las tarjetas de prueba: el comportamiento no se selecciona desde el Panel ni desde la API, sino que está determinado por el número de cuenta que uses.

### Cuentas de prueba para devoluciones ACH

Número de cuenta | Comportamiento esperado
-----------------|------------------------
1111111111 | Aprueba la transacción y permanece aprobada.
2222222222 | Rechaza la transacción.
3333333333 | Aprueba y, **5 minutos después**, genera una devolución con código NACHA **R01 (Fondos insuficientes)**.
4444444444 | Aprueba y, **5 minutos después**, genera una devolución con código NACHA **R09 (Fondos no liberados)**.
5555555555 | Aprueba y, **5 minutos después**, genera una devolución con código NACHA **R02 (Cuenta cerrada)**.

Estas cuentas se usan con el instrumento `account` y el servicio `EBACH`, con cualquier `bankCode` y `accountType` válidos:

```json
"account": {
  "bankName": "Test Bank",
  "bankCode": "041215854",
  "accountType": "SAV",
  "accountNumber": "3333333333"
}
```

Si tu sitio tiene habilitada la validación de cuentas, estas cuentas también son aprobadas por el simulador de Account Validator, así que el flujo completo (validación de cuenta → cobro → devolución) se puede ejecutar en pruebas.

### Comportamiento de las cuentas con devolución

1. La transacción se aprueba de inmediato y el comercio recibe la respuesta de aprobación normal.
2. Transcurridos **5 minutos**, se genera de forma automática y asíncrona la devolución. No requiere ninguna acción del comercio y no se puede ejecutar antes de ese tiempo.
3. La transacción original queda marcada como reversada (`refunded`) y se crea una transacción hija de tipo `CHARGEBACK` asociada a ella.
4. Se envía el [Webhook de devoluciones ACH](/payments/external-redirects/ach-bank-debit#notificacion-de-webhook-para-devoluciones-ach), el mismo que se usa en producción.

Los campos específicos de la devolución se completan así:

Campo | Valor
------|------
`reason` | El código NACHA de la cuenta usada (`R01`, `R09` o `R02`).
`originalTransactionDate` | Fecha de la transacción original (padre).
`clientBankAccountNumber` | Número de cuenta bancaria de la transacción original.
`bankRoutingNumber` | Número de ruta bancaria (`bankCode`) de la transacción original.
`processBatchId` | Número de lote de la transacción original.
`returnId` | Identificador de devolución simulado, de 4 dígitos.
`returnDate` | Fecha posterior a la de la transacción original.
`returnData` | Los primeros 9 dígitos en cero seguidos del número de autorización (CUS) de la transacción original.

La devolución simulada es visible en el Panel administrativo y en las [APIs de consulta](/gateway/api/reference/transaction) igual que una devolución real. Para entender cómo identificarla y qué significa cada campo, revisa [Devoluciones ACH](/payments/external-redirects/ach-bank-debit).
