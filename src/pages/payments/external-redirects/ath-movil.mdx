ATH Móvil permite que el pagador autorice la transacción desde su teléfono. El comercio puede ofrecer este medio de pago mediante el checkout de Placetopay o integrarlo directamente en su propia experiencia mediante Gateway.

## Beneficios de ATH Móvil {{ id: 'benefits' }}

- **Cobros mediante Push Payment**: La solicitud llega a la aplicación ATH Móvil para que el pagador mantenga el control y confirme la transacción desde su teléfono.
- **Captura mínima de datos**: En la integración por Gateway, el único dato del medio de pago que el comercio solicita al usuario es su número de teléfono.
- **Experiencia propia del comercio**: Gateway permite iniciar el cobro desde una interfaz web, móvil, IVR o un proceso asistido, sin mostrar un checkout de Placetopay.
- **Sin datos de tarjeta**: El comercio no solicita ni almacena información sensible de tarjetas para iniciar el pago.

## Casos de uso {{ id: 'use-cases' }}

- **Comercio electrónico**: El comprador selecciona ATH Móvil en Webcheckout o en la interfaz propia del comercio y confirma el pago desde su teléfono.
- **Call Centers con Gateway**: Un agente captura el número de teléfono e inicia el cobro mientras el cliente aprueba de forma privada en ATH Móvil.
- **IVR (Interactive Voice Response) con Gateway**: Un flujo de audiorespuesta recopila el teléfono y genera la solicitud sin pedir datos de tarjeta.
- **Procesos asistidos con Gateway**: Ideal para ventas o recaudos donde no existe una interfaz de pago tradicional y un operador inicia la transacción.

## Comportamiento del medio de pago {{ id: 'payment-method-behavior' }}

ATH Móvil puede operar mediante Webcheckout o una integración directa por Gateway. En ambos casos, la aprobación se completa en la aplicación ATH Móvil del pagador y la transacción se actualiza con el resultado.

### Flujo en Webcheckout {{ id: 'webcheckout-flow' }}

![Flujo de pago ATH Móvil en Webcheckout](/payments/ath-movil/pm-ath-movil-flow.png)

1. El usuario selecciona **ATH Móvil** como medio de pago.
2. El usuario completa su información y confirma el pago.
3. El pago queda en estado pendiente mientras el usuario aprueba desde su teléfono.
4. Webcheckout consulta periódicamente el estado de la transacción.
5. Cuando cambia el estado, la sesión se actualiza y muestra el resultado final al usuario.

- **Integraciones por**: [Webcheckout](/checkout)
  El usuario aprueba el pago desde su teléfono y la sesión de Checkout se actualiza con el estado final de la transacción.

## Integración por Gateway {{ id: 'gateway-integration' }}

La integración por [Gateway](/gateway) es un flujo asíncrono en el que el comercio controla la interfaz y consulta el estado por API hasta obtener el resultado final.

### Flujo directo por API {{ id: 'direct-api-flow' }}

La integración directa por Gateway permite cobrar con ATH Móvil sin redirigir al usuario ni mostrar una interfaz o checkout de Placetopay. El comercio presenta su propio componente visual y captura únicamente el número de teléfono asociado a ATH Móvil como dato del medio de pago.

Además del teléfono, el backend del comercio envía las credenciales de autenticación, la referencia y el monto requeridos para procesar la transacción.

1. El comercio muestra su propio botón o formulario de pago con ATH Móvil.
2. El usuario ingresa el número de teléfono asociado a su cuenta ATH Móvil.
3. El backend del comercio envía la solicitud a `POST /gateway/process`.
4. ATH Móvil envía una notificación push al teléfono del usuario y la transacción queda en estado `PENDING`.
5. El usuario aprueba o rechaza la solicitud desde la aplicación ATH Móvil.
6. El comercio consulta la transacción con el `internalReference` y actualiza su propia interfaz con el resultado final.

<Note>
Los nombres técnicos `instrument.redirection` y `requireRedirection` representan una autorización externa dentro del contrato de Gateway. En producción no implican redirigir al usuario ni abrir un checkout de Placetopay.
</Note>

### Implementación por API {{ id: 'implementation-sequence' }}

1. Opcionalmente, consulta las capacidades de ATH Móvil mediante `POST /gateway/information`.
2. Envía el cobro mediante `POST /gateway/process`.
3. Conserva el `internalReference` de la respuesta inicial.
4. Consulta `POST /gateway/query` mientras el estado sea `PENDING` y detente cuando recibas un resultado final.

Los ejemplos cURL de las siguientes secciones muestran cómo construir y enviar cada petición REST. Las respuestas muestran los datos que el comercio debe procesar en cada paso.

### Operaciones posteriores {{ id: 'post-transaction-operations' }}

ATH Móvil permite realizar reversos y reembolsos mediante las operaciones generales de Gateway. Su disponibilidad depende del estado de la transacción y de la configuración del sitio.

Para realizar estas operaciones, consulta [Operaciones sobre una transacción](/gateway/api/reference/transaction#transaction-request).

Los reversos deben realizarse antes de la conciliación. Una vez conciliada la transacción, corresponde realizar un reembolso. Una transacción de reembolso no puede ser reversada.

## Restricciones y consideraciones {{ id: 'validations' }}

- **Flujo asíncrono en Gateway**: El comercio debe implementar la consulta de estado por API hasta obtener un resultado final.
- **Estado pendiente durante la aprobación**: La transacción permanece pendiente mientras el usuario confirma el pago en su teléfono.
- **Disponibilidad por región**: ATH Móvil aplica para operaciones en Puerto Rico.

La petición de procesamiento admite montos decimales, los impuestos `stateTax`, `municipalTax` y `reducedStateTax` en `payment.amount.taxes`, y propinas mediante `payment.amount.details` con `kind: "tip"`. El monto base resultante después de restar estos impuestos y la propina debe ser mayor que cero.

## Casos de prueba {{ id: 'sandbox-test-cases' }}

En sitios de prueba, el simulador determina el comportamiento a partir de `payer.mobile`. Se recomienda usar el formato internacional con el prefijo `+1`; Gateway también puede normalizar números válidos de diez dígitos.

| Teléfono | Resultado esperado |
| --- | --- |
| `+19391111111` | La transacción permanece en `PENDING` antes de expirar y posteriormente finaliza en `REJECTED`. |
| `+19391111112` | La consulta finaliza en `REJECTED` por cancelación. |
| `+19391111113` | La consulta finaliza en `FAILED`. |
| `+19391111114` | La consulta finaliza en `APPROVED`. |
| `+19391111115` | El simulador retorna `REFUNDED` y Gateway normaliza el resultado a `APPROVED`. |
| `+19391111116` | El simulador retorna `REVERSED` y Gateway normaliza el resultado a `APPROVED`. |
| `+19391111117` | La consulta finaliza en `FAILED` por token expirado. |
| `+19391111118` | La consulta simula un error interno y la transacción permanece en `PENDING`. |
| `+19391111119` | La autorización de la transacción falla. |
| `+19391111120` | La consulta simula un timeout y la transacción permanece en `PENDING`. |
| `+19391111121` | El reembolso simula un timeout. |
| `+19391111122` | El reverso simula un timeout. |
| `+19391111123` | La autorización simula un timeout. |
| `+19391111169` | El procesamiento falla inmediatamente por un error de conexión. |
| `+19391111178` | El procesamiento falla inmediatamente por token expirado. |
| `+19391111190` | El procesamiento falla inmediatamente por timeout. |
| Cualquier otro número | La transacción sigue el flujo aprobado por defecto. |

## FAQs {{ id: 'faqs' }}

<details>
<summary>¿Cómo configurar ATH Móvil en tu cuenta de Placetopay?</summary>
<p>Contacta a nuestro equipo de operaciones para habilitar esta funcionalidad en tus sitios a través del correo servicioposventa@placetopay.com.</p>

<details>
<summary>¿Cómo puedo integrar ATH Móvil?</summary>
<p>ATH Móvil está disponible en Webcheckout y mediante integración directa por Gateway. Con Gateway, el comercio captura el teléfono, procesa la transacción y consulta su estado por API hasta obtener el resultado final.</p>
</details>

<details>
<summary>¿Debo redirigir al usuario en una integración Gateway?</summary>
<p>No en producción. El usuario aprueba el cobro desde la aplicación ATH Móvil y el comercio consulta el resultado con la referencia interna. La URL de redirección solo se entrega en sandbox para acceder al simulador.</p>
</details>
