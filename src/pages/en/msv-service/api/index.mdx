# MSV Service API Reference

Welcome to the MSV Service technical reference. Our API is built under RESTful principles, uses **JSON** for data exchange, and standard HTTP response codes.

<ApiDownloads />

## What is MSV Service?
MSV Service (Multi Step Validator) sends messages to an end user via WhatsApp, SMS, or Email using two modes:

- **Notification:** delivers an informational message. It ends there: no token is generated, the status cannot be queried, and no response is sent back.
- **Validation:** delivers a message with a link for the user to approve or reject. The service notifies you of the response via webhook, and you can query the status at any time.

## Environments and base URL

All requests must be sent to the following base URL, depending on your environment:

| Environment | Base URL |
| :--- | :--- |
| **Production** | `https://msv-service.placetopay.com/` |
| **UAT** | `https://msv-service-uat.placetopay.net` |
| **Develop** | `https://msv-service-dev.placetopay.ws` |

## Validation lifecycle

1. You create the request with `POST /api/validations`. The service sends the message through the channels you indicated. If at least one channel delivers it, it responds `201` with a `token` and the validation is created with status `PENDING`. If no channel delivers it, it responds `400` and the validation is set to `FAILED`.
2. The message takes the user to a confirmation page hosted by msv-service, where they approve or reject. In SMS and email, the link is added automatically; in WhatsApp, it only appears if you include `[URL_VALIDATION]` among the template parameters.
3. As soon as they respond, the request changes to `APPROVED` or `REJECTED` and the webhook is sent.
4. If they do not respond within `minutes_by_expire` (30 minutes by default, maximum 60), the request changes to `PARTIAL_EXPIRED` and the webhook is also sent.

| Status | Meaning |
| :--- | :--- |
| `PENDING` | Created, waiting for the user to respond. |
| `APPROVED` | The user approved. |
| `REJECTED` | The user rejected. |
| `PARTIAL_EXPIRED` | The time limit expired without a response. |
| `FAILED` | No channel confirmed delivery of the message. No webhook is sent. |

## Channel results {{ id: 'channel-results' }}

The responses of `POST /api/validations` and `POST /api/notifications` include a `channels` array with the result of each channel, in the same order you sent them. A channel can fail even if another one delivered the message; in that case the response is still successful.

| Field | Type | Description |
| :--- | :--- | :--- |
| `channel` | string | Channel: `sms`, `whatsapp` or `email`. |
| `delivered` | boolean | `true` if the provider accepted the message. |
| `reason` | string | Failure reason. Only present when `delivered` is `false`. |
| `message` | string | Description of the reason in the request language. Only present when `delivered` is `false`. |

If the `locale` you send is not supported, the service default language (`en`) is used.

### Failure reasons

| `reason` | Meaning |
| :--- | :--- |
| `invalid_destination` | The destination number or email is invalid or cannot receive messages. |
| `template_rejected` | WhatsApp rejected the message template. |
| `provider_unavailable` | The messaging service is not available at this time. |
| `rate_limited` | The provider's sending limit was exceeded. Try again later. |
| `authentication_error` | Authentication error with the messaging provider. It does not depend on the data you sent. |
| `delivery_unconfirmed` | The provider did not respond in time. The message may or may not have arrived. |
| `unknown` | Unexpected error when sending through the channel. |

<Note>
  msv-service does not retry deliveries. If a provider does not respond within the time limit, the channel is reported as `delivery_unconfirmed`.
</Note>

## Webhook {{ id: 'validation-webhook' }}

When the user responds to the validation or when the validation expires without a response, **msv-service** asynchronously sends a `POST` to the `webhook_url` you configured. This payload **IS NOT** the synchronous response from the `/api/validations` endpoint. It arrives later and is a notification that your server must receive and process.

### Signature validation

Before processing the webhook, recalculate the SHA-256 hash and compare it with the value received in the `signature` field. If the calculated signature matches the provided signature, the authenticity of the response is validated and you can proceed to persist the record in the database:

```php
$calculated = hash('sha256', $token . $status . $date . $secret_token);
// Example: hash('sha256', 'd5d67dcbAPPROVED2022-08-08T17:23:49+00:00ABCD1234')

if (!hash_equals($calculated, $signature)) {
    // Reject — not authentic
    http_response_code(400);
    exit;
}

// Process the webhook
http_response_code(200);
```

<Note>
  Respond `200` as soon as you validate the signature. If your server is not available at that moment, msv-service will not detect it: the delivery is delegated to an asynchronous process, so treat the webhook as a best-effort notice and reconcile with [Validation query](/en/msv-service/api/validation-query) the requests for which you have not received a response.
</Note>

<Note>
  Under no circumstances expose your `secret_token` in any part accessible to your application's clients or users.
</Note>

## Response codes

| Code | When it occurs |
| :--- | :--- |
| `200` / `201` | The request was processed and at least one channel delivered the message. |
| `400` | No channel was able to deliver the message. The per-channel detail is in `channels`. |
| `401` | The token is missing, invalid, or expired. |
| `404` | The queried token does not exist (only in validation query). |
| `422` | The data did not pass validation; the details are in `errors`. |
| `429` | You have exceeded the limit of 60 requests per minute. |
