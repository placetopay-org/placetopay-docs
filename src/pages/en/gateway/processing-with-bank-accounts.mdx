# Processing with bank accounts

To process transactions using a bank account as a payment instrument, it is necessary to implement the account payment instrument that allows defining the account data to be used, as well as the mechanisms to validate the account using account validation services such as: Account Validator.

## Resources

#### [Processing API](/en/gateway/api/reference/transaction)
#### [Account validator API](/en/account-validator)

## Bank account instrument

```json
 "account": {
    "bankName": "Test Bank",
    "bankCode": "0001234",
    "accountType": "SAV",
    "accountNumber": "4111111111111111"
  }
```

### Type of bank accounts

Type | Description
-----|----------
 SAV | Personal savings account
 DDA | Personal checking account
 CCD | Business account

## Account validation

To ensure security in bank account processing, it is recommended to use the Account Validator bank account validation service.

With this service, before initiating the payment, the account owner is required to perform a verification operation in a graphical interface.

Once the account owner completes this process, the service is consulted via API and the Account object is obtained with a verification code delivered by the service.

The processing API will be in charge of validating this code delivered by Account Validator and determining if the account has passed the validations, if not, the processing will not continue.

## Tokenization

A bank account can be tokenized in such a way that charges can be made to said account without the account owner being present.

In this flow, once the account has been validated, a token that represents the account can be generated and can be used to make new transactions.

Check the section [Tokenization](/en/gateway/api/reference/tokenize) of the API.

## ACH Return simulator

<Note>
    This simulator is exclusive to the test environment. It does **not** reproduce the real ACH return generation process between Placetopay and the banking networks, and it **does not imply any kind of certification**, neither of your integration nor between Placetopay and the return processes. Its only purpose is to let you validate, in test, the events, statuses and notifications (Webhooks) you would receive if a real ACH return happened in production.
</Note>

In production, ACH Returns are generated by processes external to Placetopay and are later captured, enriched and notified through a Webhook. That flow cannot be truly replicated in test, so test accounts with a fixed behaviour, tied to the account number, were enabled. It works just like the test cards: the behaviour is not selected from the Panel or the API, it is determined by the account number you use.

### Test accounts for ACH Returns

Account number | Expected behavior
---------------|------------------
1111111111 | The transaction is approved and stays approved.
2222222222 | The transaction is rejected.
3333333333 | Approved and, **5 minutes later**, returned with the NACHA code **R01 (Insufficient funds)**.
4444444444 | Approved and, **5 minutes later**, returned with the NACHA code **R09 (Uncleared funds)**.
5555555555 | Approved and, **5 minutes later**, returned with the NACHA code **R02 (Account closed)**.

These accounts are used with the `account` instrument and the `EBACH` service, with any valid `bankCode` and `accountType`:

```json
"account": {
  "bankName": "Test Bank",
  "bankCode": "041215854",
  "accountType": "SAV",
  "accountNumber": "3333333333"
}
```

If your site has account verification enabled, these accounts are also approved by the Account Validator simulator, so the whole flow (account verification → charge → return) can be run in test.

### Behavior of the accounts with a return

1. The transaction is approved right away and the merchant receives the regular approval response.
2. After **5 minutes**, the return is generated automatically and asynchronously. It requires no action from the merchant and it cannot be triggered earlier.
3. The original transaction is flagged as refunded and a child transaction of type `CHARGEBACK` is created and linked to it.
4. The [ACH return Webhook](/en/payments/external-redirects/ach-bank-debit#webhook-notification-for-ach-returns) is sent, the same one used in production.

The return specific fields are populated as follows:

Field | Value
------|------
`reason` | The NACHA code of the account used (`R01`, `R09` or `R02`).
`originalTransactionDate` | Date of the original (parent) transaction.
`clientBankAccountNumber` | Bank account number of the original transaction.
`bankRoutingNumber` | Bank routing number (`bankCode`) of the original transaction.
`processBatchId` | Batch number of the original transaction.
`returnId` | Simulated 4 digit return identifier.
`returnDate` | A date after the original transaction's date.
`returnData` | The first 9 digits in zero followed by the authorization number (CUS) of the original transaction.

The simulated return is visible in the administrative Panel and in the [query APIs](/en/gateway/api/reference/transaction) just like a real return. To understand how to identify it and what each field means, see [ACH Returns](/en/payments/external-redirects/ach-bank-debit).
