# Response codes

Web Checkout responses provide the information needed to determine whether an operation succeeded, is pending, or could not be processed. Understanding these values helps you implement safe retries, display useful messages, and avoid relying on text that may change by language or version.

## How to read a response

For responses from the classic Web Checkout API, inspect the values in this order:

1. **HTTP status code**: describes the request at the transport and API level.
2. **`status.status`**: describes the operation or transaction state.
3. **`status.reason`**: identifies the cause or condition with a stable code.
4. **`status.message`**: provides additional information for diagnostics or display.

Do not use `status.message` as a business identifier. It may be localized, may change, and in some operations comes from the payment service that processed the transaction.

An HTTP-successful API response does not always mean that the payment was approved. For example, an HTTP `200` response can contain `REJECTED` or `PENDING`.

```json
{
  "status": {
    "status": "FAILED",
    "reason": "request_not_valid",
    "message": "The transaction does not exist",
    "date": "2025-01-21T21:20:07-05:00"
  }
}
```

## Operation states

| State | Meaning | Recommended action |
| --- | --- | --- |
| `OK` | The API operation was processed successfully. | Continue with the response and validate the session or transaction state when applicable. |
| `APPROVED` | The transaction was approved. | Confirm the result and store the internal reference. |
| `APPROVED_PARTIAL` | The operation was partially approved. | Review the approved amount and response details. |
| `PENDING` | The final result is not available yet. | Query the session or wait for the notification; do not duplicate the operation. |
| `PENDING_VALIDATION` | The transaction requires additional validation. | Follow the flow required by the payment method. |
| `PENDING_CONFIRMATION` | The transaction requires confirmation or a subsequent action. | Use the corresponding action when the transaction state allows it. |
| `REJECTED` | The operation was rejected by a business rule, issuer, or payment service. | Review `reason` and decide whether to inform the customer or request another payment method. |
| `FAILED` | The request could not be processed. | Correct the request, review the configuration, or retry only when the cause allows it. |

## Classic API errors

These codes identify errors generated by Web Checkout before or during an API operation. They are normally returned inside `status`.

| Code | Context | Meaning | Recommended action |
| --- | --- | --- | --- |
| `request_not_valid` | Request | Required data is missing, a value is invalid, or the operation does not match the request. | Review required fields, types, amounts, and the requested action. |
| `payer_data_missing` | Session creation | Required payer data is missing. | Complete the fields indicated by the message. |
| `payer_data_not_valid` | Session creation | Payer data does not meet validation rules. | Correct the data format and values. |
| `shipping_address_data_not_valid` | Session creation | The shipping address is invalid. | Review the address fields and formats. |
| `metadata_not_valid` | Session creation | Metadata does not match the allowed structure or rules. | Correct the submitted keys and values. |
| `unauthorized` | Resource access | The merchant cannot access the requested session or transaction. | Verify credentials and resource ownership. |
| `action_not_allowed` | Cancellation or transaction action | The action is not allowed for the current state. | Query the state and use the corresponding action. |
| `external_service_failed` | Cancellation or external service | An external service required by the operation failed. | Check the operation state before retrying. |
| `transaction_request_error` | `transaction`, `reverse`, and transaction actions | The request could not be completed against the payment service. | Verify the transaction result and retry with idempotency control. |
| `transaction_modifier_not_matched_error` | Modifiers | Modifier agreements do not match the configuration. | Review modifiers and merchant configuration. |
| `transaction_modifiers_site_sync_error` | Modifiers | Merchant modifiers could not be synchronized. | Check configuration and contact support if the issue persists. |
| `max_dispersion_error` | Dispersion | The maximum number of dispersions was reached. | Reduce dispersions or review the configuration. |
| `transaction_modifiers_max_dispersion_error` | Modifiers and dispersion | The maximum number of modifier dispersions was reached. | Review configured agreements and limits. |
| `autopay_edit_sync_error` | Autopay | An autopay edit could not be synchronized. | Query the state before sending another modification. |

### Example: invalid request

```json
{
  "status": {
    "status": "FAILED",
    "reason": "request_not_valid",
    "message": "The reference is invalid",
    "date": "2025-01-21T21:20:07-05:00"
  }
}
```

### Example: external service unavailable

```json
{
  "status": {
    "status": "FAILED",
    "reason": "transaction_request_error",
    "message": "The external service could not be reached, please try again in a few minutes",
    "date": "2025-01-21T21:20:07-05:00"
  }
}
```

## Web Checkout V4 errors

V4 endpoints return the reason directly in the response, without the `status` object used by the classic API.

```json
{
  "reason": "session_not_found",
  "message": "The provided session does not exist."
}
```

### Session and request

| Code | Meaning | Recommended action |
| --- | --- | --- |
| `not_valid_params` | Required route or request parameters are missing. | Review the parameters required by the endpoint. |
| `not_valid_salt` | The session identifier or salt is invalid. | Use the URL and identifier returned when the session was created. |
| `session_not_found` | The session does not exist. | Verify the identifier and environment. |
| `session_expired` | The session has expired. | Create a new session. |
| `session_not_in_progress` | The session cannot continue its current flow. | Query its state and do not process it again. |
| `inactive_session` | The session is inactive or locked. | Query the session or start a new flow. |
| `site_not_found` | The site configured for the operation was not found. | Review the merchant configuration. |
| `transaction_not_found` | The requested transaction was not found. | Verify the reference and environment. |
| `not_valid_signature` | The received signature is invalid. | Verify the signature and notification credentials. |

| `not_valid_payer_provided` | Payer data is invalid. | Correct the payer data. |

| `card_expiration_not_valid` | Card expiration is invalid. | Correct the date or request another payment method. |
| `not_valid_credit_id` | The credit option or installment count is invalid. | Review the options available for the instrument. |

## Gateway-dependent responses

For payment, confirmation, refund, and reverse operations, the state and `reason` may reflect the response from the gateway, bank, card network, or processor. You may therefore see codes such as `00`, `05`, `?-`, `?!`, `BR`, `XH`, `XN`, or `XR`.

These codes describe the transaction result in the payment network and do not necessarily represent a Web Checkout error. For their full meaning, see the [Gateway Transactions API](/en/gateway/api/reference/transaction).

For example, a reverse can return HTTP `200` with a rejected transaction:

```json
{
  "status": {
    "status": "REJECTED",
    "reason": "05",
    "message": "Declined",
    "date": "2025-01-21T21:20:07-05:00"
  }
}
```

## Transaction actions

### Reverse

The `POST /api/reverse` endpoint forces the `reverse` action and requires the transaction's internal reference. An approved reverse returns `APPROVED` with reason `00`. A communication failure may return `FAILED` with `transaction_request_error`; a gateway rejection may return `REJECTED` with the code provided by the processor.

Before retrying a reverse, query the transaction state. This prevents duplicate operations when the external service received the request but Web Checkout did not receive the response.

### Refunds and other actions

The `checkout`, `reauthorization`, `confirm`, and `cancel` actions have different rules depending on the session type and state. See [Transaction actions](/en/checkout/api/reference/payment#transaction-actions) and [Refunds](/en/checkout/refund) for their conditions and examples.

## Best practices

- Use `status` and `reason` to classify responses; do not use `message` as a code.
- Log the endpoint, HTTP code, `status`, `reason`, date, and internal reference.
- Do not automatically retry an operation with an indeterminate result without checking the transaction first.
- Use backoff for external service errors and request limits.
- Implement a default case for new codes or codes returned by a gateway.
- Do not expose credentials, keys, nonces, or internal traces in logs or user-facing messages.
