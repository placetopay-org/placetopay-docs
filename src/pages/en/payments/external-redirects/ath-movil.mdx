ATH Móvil allows the payer to authorize the transaction from their phone. Merchants can offer this payment method through Placetopay Checkout or integrate it directly into their own experience through Gateway.

## ATH Móvil Benefits {{ id: 'benefits' }}

- **Push payments**: The request reaches the ATH Móvil application so the payer remains in control and confirms the transaction from their phone.
- **Minimal data capture**: With Gateway integration, the only payment-method data requested from the user is their phone number.
- **Merchant-owned experience**: Gateway can initiate the payment from a web, mobile, IVR, or assisted process without displaying a Placetopay checkout.
- **No card data**: The merchant does not request or store sensitive card information to initiate the payment.

## Use Cases {{ id: 'use-cases' }}

- **E-commerce**: Buyers select ATH Móvil in Webcheckout or in the merchant's interface and confirm the payment from their phone.
- **Call centers with Gateway**: An agent captures the phone number and initiates the charge while the customer privately approves it in ATH Móvil.
- **IVR (Interactive Voice Response) with Gateway**: An automated voice flow collects the phone number and creates the request without asking for card data.
- **Assisted processes with Gateway**: Ideal for sales or collection flows without a traditional payment interface, where an operator initiates the transaction.

## Payment Method Behavior {{ id: 'payment-method-behavior' }}

ATH Móvil can operate through Webcheckout or direct Gateway integration. In both cases, approval is completed in the payer's ATH Móvil application and the transaction is updated with the result.

### Webcheckout Flow {{ id: 'webcheckout-flow' }}

![ATH Móvil payment flow in Webcheckout](/en/payments/ath-movil/pm-ath-movil-flow.png)

1. The user selects **ATH Móvil** as the payment method.
2. The user completes their payment information and confirms the payment.
3. The payment remains pending while the user approves from their phone.
4. Webcheckout periodically checks the transaction status.
5. When the status changes, the session updates and shows the final result.

- **Integrations through**: [Webcheckout](/en/checkout)
  The user approves the payment from their phone and the Checkout session updates with the final transaction outcome.

### Confirmation timeout {{ id: 'confirmation-timeout' }}

When creating a Webcheckout session, you can send [`metadata.athMovilConfirmationTimeOut`](/en/checkout/metadata) to define how many minutes the payer has to confirm the payment in ATH Móvil. It is optional and, when provided, must be an integer from `1` through `60`. It applies only to ATH Móvil; if omitted or sent as `null`, the applicable configured value is used.

```json
{
  "metadata": {
    "athMovilConfirmationTimeOut": 20
  }
}
```

This timeout is independent of `CreateSessionRequest.expiration`, which controls the overall lifetime of the Webcheckout session.

## Gateway Integration {{ id: 'gateway-integration' }}

The [Gateway](/en/gateway) integration is an asynchronous flow in which the merchant controls the interface and queries the status through the API until a final result is obtained.

### Direct API flow {{ id: 'direct-api-flow' }}

Direct Gateway integration lets merchants charge with ATH Móvil without redirecting the user or displaying a Placetopay interface or checkout. The merchant presents its own visual component and captures only the phone number associated with ATH Móvil as payment-method data.

In addition to the phone number, the merchant backend sends the authentication credentials, reference, and amount required to process the transaction.

1. The merchant displays its own ATH Móvil payment button or form.
2. The user enters the phone number associated with their ATH Móvil account.
3. The merchant backend sends the request to `POST /gateway/process`.
4. ATH Móvil sends a push notification to the user's phone, and the transaction remains `PENDING`.
5. The user approves or rejects the request in the ATH Móvil application.
6. The merchant queries the transaction using the `internalReference` and updates its own interface with the final result.

### API implementation {{ id: 'implementation-sequence' }}

1. Optionally query ATH Móvil capabilities through `POST /gateway/information`.
2. Send the charge through `POST /gateway/process`.
3. Store the `internalReference` from the initial response.
4. Query `POST /gateway/query` while the status is `PENDING`, and stop when a final result is returned.

The cURL examples in the following sections show how to build and send each REST request. The responses show the data the merchant must process at each step.

### Post-transaction operations {{ id: 'post-transaction-operations' }}

ATH Móvil supports reversals and refunds through the general Gateway operations. Their availability depends on the transaction status and site configuration.

To perform these operations, see [Operations on a transaction](/en/gateway/api/reference/transaction#transaction-request).

Reversals must be performed before reconciliation. Once the transaction is reconciled, use a refund instead. A refund transaction cannot be reversed.

## Restrictions and Considerations {{ id: 'validations' }}

- **Asynchronous Gateway flow**: The merchant must implement API status polling until a final result is available.
- **Pending state during approval**: The transaction remains pending while the user confirms the payment on their phone.
- **Regional availability**: ATH Móvil applies to operations in Puerto Rico.

The processing request supports decimal amounts; `stateTax`, `municipalTax`, and `reducedStateTax` in `payment.amount.taxes`; and tips through `payment.amount.details` with `kind: "tip"`. The base amount remaining after subtracting these taxes and the tip must be greater than zero.

## Test cases {{ id: 'sandbox-test-cases' }}

For test sites, the simulator determines its behavior from `payer.mobile`. International format with the `+1` prefix is recommended; Gateway can also normalize valid ten-digit numbers.

| Phone | Expected result |
| --- | --- |
| `+19391111111` | The transaction remains `PENDING` before expiration and later ends in `REJECTED`. |
| `+19391111112` | The query ends in `REJECTED` due to cancellation. |
| `+19391111113` | The query ends in `FAILED`. |
| `+19391111114` | The query ends in `APPROVED`. |
| `+19391111115` | The simulator returns `REFUNDED`, and Gateway normalizes the result to `APPROVED`. |
| `+19391111116` | The simulator returns `REVERSED`, and Gateway normalizes the result to `APPROVED`. |
| `+19391111117` | The query ends in `FAILED` due to an expired token. |
| `+19391111118` | The query simulates an internal error, and the transaction remains `PENDING`. |
| `+19391111119` | Transaction authorization fails. |
| `+19391111120` | The query simulates a timeout and the transaction remains `PENDING`. |
| `+19391111121` | The refund simulates a timeout. |
| `+19391111122` | The reversal simulates a timeout. |
| `+19391111123` | Authorization simulates a timeout. |
| `+19391111169` | Processing fails immediately due to a connection error. |
| `+19391111178` | Processing fails immediately due to an expired token. |
| `+19391111190` | Processing fails immediately due to a timeout. |
| Any other phone number | The transaction follows the default approved flow. |

## FAQs {{ id: 'faqs' }}

<details>
<summary>How do I enable ATH Móvil in my Placetopay account?</summary>
<p>Contact our operations team to enable this functionality for your sites at servicioposventa@placetopay.com.</p>
</details>

<details>
<summary>How can I integrate ATH Móvil?</summary>
<p>ATH Móvil is available through Webcheckout and direct Gateway integration. With Gateway, the merchant captures the phone number, processes the transaction, and queries its status through the API until a final result is returned.</p>
</details>

<details>
<summary>Should I redirect the user in a Gateway integration?</summary>
<p>Not in production. The user approves the charge from the ATH Móvil application, and the merchant queries the result using the internal reference. The redirection URL is provided only in sandbox to access the simulator.</p>
</details>
