ATH Móvil allows the payer to approve the transaction from their phone, while the merchant handles status confirmation according to the integration model.

## ATH Móvil Benefits {{ id: 'benefits' }}

- **Instant transfers**: Send and receive money in real time using a mobile phone number.
- **Broad financial participation**: Works with participating banks and credit unions in the ATH Móvil ecosystem.
- **Security and speed for daily transactions**: Delivers a secure experience for everyday payments and transfers.

## Use Cases {{ id: 'use-cases' }}

- **Merchants in Puerto Rico**: Ideal for businesses that want to enable ATH Móvil as a local payment option.
- **Second-device payment approval**: The buyer confirms the transaction on their phone while keeping checkout open.

## Payment Method Behavior {{ id: 'payment-method-behavior' }}

ATH Móvil is categorized as a redirection payment method in the integration model, where approval is completed on the payer's phone and the session is updated with the transaction status.

![ATH Móvil payment flow](/en/payments/ath-movil/pm-ath-movil-flow.png)

### Webcheckout Flow {{ id: 'webcheckout-flow' }}

1. The user selects **ATH Móvil** as the payment method.
2. The user completes their payment information and confirms the payment.
3. The payment remains pending while the user approves from their phone.
4. Webcheckout periodically checks the transaction status.
5. When the status changes, the session updates and shows the final result.

- **Integrations through**: [Webcheckout](/en/checkout)
  The user approves the payment from their phone and the Checkout session updates with the final transaction outcome.

## Gateway Integration {{ id: 'gateway-integration' }}

[Gateway](/en/gateway) integration is asynchronous. After creating or processing the transaction, the integrator must query its status via API until the final result is obtained.

To obtain the final status, send a request to [Query transaction by internal reference](/en/gateway/api/reference/transaction#query-request).

### Implementation sequence {{ id: 'implementation-sequence' }}

1. Query ATH Móvil capabilities through `POST /gateway/information`.
2. Send the charge through `POST /gateway/process`.
3. Store the `internalReference` from the initial response.
4. Query `POST /gateway/query` while the status is `PENDING`, and stop when a final status is returned or the expiration is reached.

The cURL examples in the following sections show how to build and send each REST request. The responses show the data the merchant must process at each step.

### Post-transaction operations {{ id: 'post-transaction-operations' }}

ATH Móvil supports reversals and refunds through the general Gateway operations. Their availability depends on the transaction status and site configuration.

To perform these operations, see [Operations on a transaction](/en/gateway/api/reference/transaction#transaction-request).

Refunds require the ATH Móvil transaction to be reconciled. A refund transaction cannot be reversed.

## Restrictions and Considerations {{ id: 'validations' }}

- **Asynchronous Gateway flow**: The merchant must implement API status polling until a final result is available.
- **Pending state during approval**: The transaction remains pending while the user confirms the payment on their phone.
- **Regional availability**: ATH Móvil applies to operations in Puerto Rico.

The processing request supports decimal amounts, taxes in `payment.amount.taxes`, and tips through `payment.amount.details` with `kind: "tip"`.

## Test cases {{ id: 'sandbox-test-cases' }}

For test sites, the simulator determines its behavior from `payer.mobile`. Always send the international `+1` prefix; without it, the expected test case will not be activated.

| Phone | Expected result |
| --- | --- |
| `+19391111111` | The transaction remains `PENDING`. |
| `+19391111112` | The query ends in `REJECTED` due to cancellation. |
| `+19391111113` | The query ends in `FAILED`. |
| `+19391111114` | The query ends in `APPROVED`. |
| `+19391111115` | The query returns a `REFUNDED` transaction. |
| `+19391111116` | The query returns a `REVERSED` transaction. |
| `+19391111117` | The query ends in `FAILED` due to an expired token. |
| `+19391111118` | The query fails due to an invalid token. |
| `+19391111119` | Transaction authorization fails. |
| `+19391111120` | The query simulates a timeout and the transaction remains `PENDING`. |
| `+19391111121` | The refund simulates a timeout. |
| `+19391111122` | The reversal simulates a timeout. |
| `+19391111123` | Authorization simulates a timeout. |
| `+19391111169` | Processing fails immediately due to a connection error. |
| `+19391111178` | Processing fails immediately due to an expired token. |
| `+19391111190` | Processing fails immediately due to a timeout. |
| Any other phone number | The transaction follows the default approved flow. |
