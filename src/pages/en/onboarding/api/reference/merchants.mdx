## Create a merchant {{ id: 'create-a-merchant', tag: 'POST', label: '/api/merchants' }}

<Row>
  <Col>
    Validates the complete merchant and accepts it for registration. The response arrives before the merchant exists: it includes a `processId` you can use to [retrieve the result](/en/onboarding/process-status).

    The request selector covers nine scenarios: the **minimum body**; a merchant **with its sites and payment methods**, which shows what a site requires you to send; the body **with every field** the request accepts; a **full-transaction merchant**; a **Webpay merchant**; a **Webpay merchant with Seglan**; a **Webpay merchant with cl-auth**; and two **POS Virtual** merchants, one **for direct payment** and one **for airline sales**. The full-transaction merchant and the Webpay merchants use a [site migrated from Copper](/en/onboarding/sites#copper-migrated-sites); the Seglan one registers the site in Seglan and the cl-auth one registers it in cl-auth, and both also require the `onboarding:enroll` permission. The airline-sales merchant uses a `POS_AIR` site and declares `travelAgency.dispersion` on the merchant.

    The three collections in the body —`integrations`, `paymentMethods`, and `sites`— have their own identity and update rules, explained in [Integrations](/en/onboarding/integrations), [Payment methods](/en/onboarding/payment-methods), and [Sites](/en/onboarding/sites).

## Update a merchant {{ id: 'update-a-merchant', tag: 'PATCH', label: '/api/merchants/{merchantId}' }}

<Row>
  <Col>
    Write only the fields the body names. The rest of the merchant keeps its value, and no field is required — but the body must name at least one: a `{}` returns `422` with the `body` error key, and a body containing only `notification` still counts as empty.

    Within collections, each item **either** updates an existing row by its identifier **or** creates a new one. A site without an `id` is a site that gets created, which makes all its fields required again: the error states it explicitly, `The sites.0.displayName field is required when sites.0.id is not present.`

    <Note>
      When updating, a site enables one of the merchant's payment methods with **`paymentMethodId`**, not `code` — including a site that this same request is creating, because that identifier points to a row of the **merchant**, which exists. This is the opposite of creating the merchant, where `code` is the only possible option. Details are in [Site payment methods](/en/onboarding/site-payment-methods).

      In the root-level `paymentMethods`, the **values** travel alongside `id` —`accountNumber`, `accountType`, `commissionModel`, `commissionValue`, `order`, `creditRules`, `settings`—, but not the **identity**: restating `code` or `financialEntity` returns `422` even when the value is the one the row already has.
    </Note>
